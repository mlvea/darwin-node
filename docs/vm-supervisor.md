# Per-VM supervisor

darwin-node can run each pod VM in its own process. The agent process
watches Kubernetes and serves :10250. A supervisor process owns one
`VZVirtualMachine`. A crash, panic, or upgrade of the agent does not
destroy a VM that a supervisor already started.

The mode is off unless the process is started with `--vm-supervisor=on`.

## Roles

One binary, signed once with the virtualization entitlement.
Entitlements do not cross `execve`, so the supervisor is not a child
helper with a different signature. It is the same `darwin-node` binary.

| Role | Flag | Job |
| --- | --- | --- |
| agent | `--role=agent` (default) | virtual-kubelet, image pull, pod watch |
| supervisor | `--role=supervisor --slot=N` | one VM, one control socket |

`N` is 0 or 1. The host cap stays two VMs.

The supervisor does not pull OCI images, watch the API server, or listen
on :10250. It creates the VM through the same runtime interface the
agent uses in-process, then serves five calls on a Unix socket.

## How a VM is launched

Production uses two LaunchAgents in the `gui/<uid>` domain:

- `io.darwin-node.slot-0`
- `io.darwin-node.slot-1`

Examples live in `deploy/launchd/`. Each one listens on
`<run dir>/slot-N.sock`. `KeepAlive` is `{SuccessfulExit=false}`: launchd
restarts a supervisor that crashes, and does not restart one that exits
0 after its VM stops. The next pod needs `launchctl kickstart
gui/$UID/io.darwin-node.slot-N`, or `--vm-supervisor-spawn=subprocess`.

The run directory is mode 0700 and owned by the service user. The agent
default is `~/Library/Application Support/io.darwin-node.node/run`. The
plist example uses `/var/lib/darwin-node/run`, which the GUI user must
create before the first boot. launchd does not create it, and the plist
does not use a `Sockets` key. The process binds the socket itself.

The socket path has to fit in `sockaddr_un.sun_path`: 103 bytes on macOS
and 107 on Linux, not counting the trailing NUL. A home under
`~/Library/Application Support/io.darwin-node.node/run` fits a short
account name. A longer path fails at startup with the length in the
error. `/var/lib/darwin-node/run` stays well under the limit.

For a checkout without launchd, `--vm-supervisor-spawn=subprocess` (the
default) starts the supervisor with `Setsid` and leaves its process
group. There is no `Pdeathsig`. If the agent dies first, init adopts the
supervisor. If the agent is still alive when the supervisor exits, a
background `Wait` reaps it.

## Control socket

The first frame is a version handshake. The supervisor sends its
protocol major, protocol minor, and binary version. The agent refuses an
unknown major and accepts any minor and any binary of the same major. A
running supervisor therefore keeps its old binary until its VM exits.
The agent then sends its own hello. A peer-uid failure is an error frame
before the hello.

After the handshake the calls are:

| Call | Effect |
| --- | --- |
| `StartVM` | create and start the only VM. The same boot id is idempotent. A different boot id while a VM exists is `slot_busy`. |
| `InspectVM` | boot id, token, pid, start time, pod identity, image digest, state. |
| `PauseAndSaveVM` | pause and write a state file. |
| `StopVM` | stop the VM. The process then exits 0. A stop with no VM does not exit. |
| `AttachChannels` | pass two file descriptors with `SCM_RIGHTS`. |

`AttachChannels` passes, in order:

1. a dup of the supervisor's end of the `SOCK_DGRAM` socketpair used as
   `VZFileHandleNetworkDeviceAttachment`;
2. a connected stream to the guest agent port. The supervisor dials
   vsock on the Virtualization queue and hands the descriptor over.

The guest-agent protocol stays between the agent and the guest. The
supervisor does not parse it.

A heartbeat call exists so a long-lived connection can refresh the
supervisor's last-seen time. The open connection itself is what holds
the dead-man switch off.

## Boot lease

Before it treats a VM as running, the agent writes
`<run dir>/slots/slot-N/lease.json` atomically (temp file, fsync,
rename). The file is mode 0600. The directories are mode 0700. The
document is:

```json
{
  "pod_uid": "",
  "pod_name": "",
  "namespace": "",
  "boot_id": "",
  "image_digest": "",
  "supervisor_pid": 0,
  "supervisor_start_time_ns": 0,
  "hmac_token": ""
}
```

`boot_id` is a random UUID. `hmac_token` is HMAC-SHA256 of the boot
identity under a random key that is then discarded. The token is the
secret. Both values are generated by the agent and echoed by the
supervisor. They are not derived from the pod uid alone.

On reattach, `InspectVM` must return the same boot id, token, pid,
start time, pod identity, and image digest. The pod must still exist
and must not have `DeletionTimestamp`. Otherwise the agent calls
`StopVM` and deletes the lease.

## Dead-man switch

The switch is armed only after a connection drops while a VM is
running. It is not armed at process start, and it is not armed when
the slot is empty. An open connection disarms it. The default wait is
5 minutes (`--vm-supervisor-deadman`). When it fires, the supervisor
stops the VM and exits 0.

`SIGTERM` and a cancelled process context also stop the VM and exit 0.
A failure to listen exits non-zero, which is what launchd restarts.

## Restart and death

A restarted node-agent re-adopts a live slot through `supervisor.Adopt`.
Adopt dials the control socket, fences the boot lease, and calls
`AttachChannels`. The guest descriptor is the one that call just
received: a fresh Connect passed with `SCM_RIGHTS`. Adopt does not take
a saved fd.

The session watches dups of the control connection and the guest fd.
The watch is edge-triggered: epoll with `EPOLLET` on Linux, kqueue with
`EV_CLEAR` on Darwin. A queued guest byte stays queued for the agent.
Peer close, including SIGKILL of the supervisor, wakes the wait.

That wake marks the slot `SlotLost`. Status becomes `VMFailed` with
message `supervisor lost`, within about 2 seconds. The watch does not
wait for the dead-man switch. The contract test sets that switch to 1
hour so a poll of the RPC would miss the bound. The operator default
stays 5 minutes (`--vm-supervisor-deadman`).

`pkg/runtime/supervised` calls Adopt on the first attach, after
`StartVM` and the lease are written, and again from `Recover`.
`Recover` does not spawn a supervisor and does not boot another VM. It
takes a fresh Connect, arms the death watch, and releases the supervisor
slot exactly once when the message is `supervisor lost`. A later `Stop`
does not free a slot a new VM has taken.

`--vm-supervisor` stays default `off`. This path is not used while the
flag is off.

`pkg/engine` still does not call the adapter's `Recover`. Its own
`Recover` only republishes cache stores and deletes unheld pod
directories. A restarted node-agent process therefore leaves a live VM
unadopted. The machine status is `Failed` / `supervisor lost`. The pod
status the engine writes is still its generic text: reason `VMFailed`,
message `macOS VM Failed unexpectedly`.

`Connect` during `Start` on real Virtualization.framework is
hardware-pending. Adopt calls `Connect` immediately. A guest that is
not listening yet can stall that call. SimVZ registers the agent during
`Start`, so the Linux tests do not show the stall.

## Peer check

On accept, the supervisor reads the peer uid. macOS uses
`LOCAL_PEERCRED` (`unix.GetsockoptXucred`). Linux, used by the tests,
uses `SO_PEERCRED` (`unix.GetsockoptUcred`). The uid must equal the
supervisor's own uid. `ENOTCONN`, and a Linux `SO_PEERCRED` that
succeeds with no peer, closes the connection and does not serve it.
That is not an authentication failure and does not stop the VM.

## Threat model

The run directory is the trust boundary.

- Mode 0700 and a matching uid stop another local user from connecting
  or from swapping `lease.json`.
- The peer-uid check stops a process that can see the socket path but
  runs as someone else. Root can still impersonate the uid; the service
  account is the boundary, not a defense against root.
- The HMAC token stops a restarted agent from adopting a VM whose lease
  was replaced, and stops a supervisor from being told a boot id that
  the agent did not write. The token is stored in the lease and in the
  supervisor. Anyone who can read the lease can replay it, which is why
  the directory is 0700.
- The supervisor does not parse the guest protocol, so a hostile guest
  cannot drive the control socket through the vsock stream. The stream
  is handed to the agent, which already speaks that protocol.
- A hostile agent that is the same uid can `StopVM`. That is the same
  privilege the in-process runtime has today.

What this does not change: the virtualization entitlement, the kubelet
TLS setup, and the guest agent's own handshake. Those stay as they are
when the flag is off.

## Upgrade

1. Install the new signed binary over the agent path.
2. Restart the agent. Supervisors that are already running are not
   restarted. They keep the previous binary.
3. The new agent handshakes. Same protocol major: it reattaches, checks
   the lease and the pod, and leaves the VM running. Different major:
   it refuses the socket. The operator stops that VM (or waits for the
   dead-man switch) and the slot's next start is the new binary.
4. When a VM stops, that supervisor exits 0. The next `StartVM` for the
   slot is a new process on the new binary.

Do not send the running supervisors `SIGKILL` as part of an upgrade.
That is the failure this design exists to avoid.

## What is still in-process when the flag is off

`--vm-supervisor=off` is the default. The agent creates
`VZVirtualMachine` values in its own process, with NAT or bridged
networking, exactly as before. The file-handle NIC is used only inside
a supervisor, and only when that process was given a vz runtime.

## Hardware-pending

These paths are implemented and compile for `darwin/arm64`. They have
not been run on Apple hardware in this change:

- A file-handle NIC actually moving frames. The socketpair, buffer
  sizes, and `VZFileHandleNetworkDeviceAttachment` call are in place.
  The agent does not yet bridge those frames to host NAT.
- `VirtioSocketDevice.Connect` on the Virtualization queue, and taking
  the unix descriptor out of the unexported `rawConn` field. v3's
  `Connect` has no context. If the guest never listens, the call may
  not return; the cancel path closes a connection that arrives later
  and can leave that goroutine waiting. Today's guest dials the host,
  so `Connect` does not complete until the guest listens. Adopt during
  `Start` calls `Connect` immediately, so that stall is on the first
  attach as well. This has not been run on a Mac Mini.
- `Pause` plus `SaveMachineStateToPath`. The save API is macOS 14. On
  macOS 13 the framework returns an error. The minimum system stays
  macOS 13.
- LaunchAgents in `gui/<uid>`, `launchctl kickstart`, and the single
  codesign of the binary. The plist text is checked in CI. launchd
  itself is not.

## Still open

- `pkg/engine` still does not call the adapter's `Recover`. A restarted
  agent with the flag on leaves a live VM unadopted. See
  [Restart and death](#restart-and-death).
- The guest agent still dials the host. `AttachChannels` dials the
  guest. Those meet when the guest listens.
- The datagram descriptor is handed to the agent and not bridged.
  A guest booted with the flag on has no host network until that
  bridge exists.
- Slot stdout and stderr are not in `deploy/launchd/darwin-node.conf`.
  Adding rules there would break the node plist test, which requires
  the newsyslog rule count to match the node plist log files.
- The supervised machine does not expose the serial console. The
  in-process console flag is unchanged.
- A recovered machine does not carry the guest-agent token. The lease
  does not store it. The engine has to supply the token from the pod
  before `DialAgent` on a reattached VM.
- After a clean supervisor exit, launchd will not start the slot again
  until `kickstart` or a subprocess spawn.
