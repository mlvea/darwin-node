# ADR 0007 — GPU / graphics (paravirtualized Metal)

- Status: Accepted
- Date: 2026-08-23
- Phase: 0 / 1 (config) / 5 (validation)

## Context

Apple does **not** offer exclusive PCIe GPU passthrough to macOS guests on
Apple Silicon. What exists is a paravirtualized graphics device:

```
VZMacGraphicsDeviceConfiguration
  └─ VZMacGraphicsDisplayConfiguration(width, height, pixelsPerInch)
```

The guest sees a virtual GPU. Metal commands are executed on the host GPU.
This is shared, not exclusive: both guests and the host contend for the same
GPU. WWDC 22 ("Create macOS or Linux virtual machines") documents that Metal
in the guest is the supported path and that display size/PPI are configurable.

Observed guest behaviour (ecosystem, 2023–2026):

- Metal works for UI, encode/decode, and many compute workloads.
- `MTLDevice.supportsFamily` often reports an older family than the host
  (e.g. Apple 5-class limits: 32 KB threadgroup memory, no SIMD-group matrix).
- Some ML stacks (llama.cpp, etc.) therefore pick slower kernels unless the
  guest is tricked into seeing a newer family. We will **not** ship family
  spoofing; we document the actual model.
- Display resolution/PPI affect the virtual framebuffer, not compute
  availability. Headless CI still needs a graphics device for Metal.

Agoda always attaches 1920×1200@80 PPI "to support VNC" and does not advertise
GPU to Kubernetes.

## Decision

1. **Always attach** `VZMacGraphicsDeviceConfiguration` unless
   `--graphics=none` (debug only). Metal will not work without it.
2. Display defaults: `1920x1200@80`. Overridable per node
   (`--graphics-width/height/ppi`) and later per-pod annotation
   `darwin.node/graphics=2560x1600@110`.
3. **Report honestly:**

   Labels:
   - `darwin.node/gpu=shared`
   - `darwin.node/gpu.model=apple-paravirtual`
   - `darwin.node/gpu.metal=true`
   - `darwin.node/gpu.passthrough=false`

   Capacity/allocatable:
   - `darwin.node/metal: 2` (one per VM slot). This is a *scheduling token*
     meaning "this pod may use the shared Metal device", not an exclusive
     GPU. We do **not** advertise `nvidia.com/gpu` or any PCIe resource.

4. Node condition `MetalReady=True` when the graphics device was configured
   successfully. False if `--graphics=none`.
5. Guest Agent `Metrics` includes best-effort GPU bytes in / bytes out if
   IORegistry yields them; otherwise omitted. No fake 100% utilization.
6. Validation (hardware e2e, documented in `docs/gpu.md`):
   - `system_profiler SPDisplaysDataType` inside the guest
   - A tiny Metal compute shader (built into guest-agent `selftest metal`)
   - Optional: `videotoolbox` encode of a 1-second buffer

## Non-goals

- Exclusive GPU assignment.
- CUDA / NVIDIA.
- Spoofing `supportsFamily` to unlock newer Metal kernels.
- GPU time-slicing guarantees between the two VMs and the host.

## Consequences

- CI workloads that need simulators / Metal / video pipelines work, with
  shared-GPU caveats.
- Schedulers that match `darwin.node/metal` can place GPU-aware pods; they
  must still fit in the 2-VM cap.
- Operators expecting A100-style isolation will be disappointed; the
  limitations doc says so in the first screen.
