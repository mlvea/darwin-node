# Limitations

darwin-node is **alpha**. The node agent was built quickly (largely with
coding agents) and still needs review and testing on real Apple Silicon
hardware. What follows is the intended contract, not a production SLA.
The software is provided AS IS; see [LICENSE](../LICENSE).

darwin-node is not a Linux kubelet. Some Kubernetes features are impossible
on Apple Silicon macOS VMs; others are degraded. This file is the contract.

## Physically or legally impossible

| Feature | Why |
|---|---|
| More than 2 concurrent macOS VMs per host | Apple EULA + XNU `hv_apple_isa_vm_quota`. Third VM -> `VZErrorVirtualMachineLimitExceeded`. |
| Nested virtualization | Virtualization.framework does not nest macOS VMs. |
| Exclusive GPU passthrough | Only paravirtualized Metal (`VZMacGraphicsDevice`). Shared with host and the other VM. |
| Intel Macs | Out of scope. Apple Silicon only. |
| Linux VM as container[0] | This project is a *macOS* node. Linux workloads belong on Linux nodes. |
| cgroups / Linux securityContext | The primary container is a full macOS guest. |
| `privileged: true` meaning host kernel | The VM is already a separate kernel. Host devices are not passed through except virtio. |
| In-place pod spec updates | Recreate. Best-effort state transfer is Phase 6. |

## Degraded (supported with caveats)

| Feature | Behaviour |
|---|---|
| NAT networking | PodIP is host-local. Cluster Services from other nodes do not reach it. Node is tainted `darwin.node/nat-only` unless `--allow-nat-workloads`. |
| Resource limits | Applied at VM *create* as a cap on vCPU/memory. Cannot be enforced after start. |
| `emptyDir.medium: Memory` | Not tmpfs; ordinary directory. |
| `emptyDir.sizeLimit` | The watch loop sums regular files on the host directory and does not follow symlinks. Over the limit, or a relative symlink that lexically leaves the directory, the pod fails and the slot is released. The pod message does not include the host path. An absolute or dangling symlink does not fail the pod. The guest can write past the limit between checks. An APFS quota that refuses the write is still future work. `medium: Memory` is a normal directory. |
| Image and cache-store disk | GC runs when the cache filesystem is at or above `--image-gc-high-threshold` (default 85) and stops at or below `--image-gc-low-threshold` (default 80). It deletes the oldest unused image or cache store and emits `ImageEvicted` or `CacheEvicted`. A pending or running pod, a warm-pool VM, the configured warm image while `--warm-slots` is non-zero, and a delta base that a remaining image still names are kept. Succeeded and failed pods do not pin their image. Age is the directory mtime from the pull, not the last pod start. `DiskPressure` is still the 90% node condition and does not itself delete anything. `emptyDir` is a per-pod `sizeLimit`, not this GC. |
| ServiceAccount token rotation | Each projected token is minted on its own. A mint error or an empty token fails pod creation. The watch loop refreshes at half the remaining lifetime, rewrites the host file, and re-copies it into the guest. Refresh keeps the last good file until the recorded expiry; after expiry a failed refresh fails the pod. |
| Init containers | Host Docker only, sequential, before the VM starts. A macOS image as an init container is rejected. |
| Crash-looping hybrid sidecar | The container waits in `CrashLoopBackOff` (10s, then 20s, doubling, capped at 5m) with that reason and a `back-off … restarting failed container` message. Same rule as kubelet: the pod stays `Running` and is not failed for looping. It keeps its VM slot until the pod is deleted. Delete during the backoff returns and frees that slot; the backoff does not sleep. Deleting the pod drops that backoff entry. The other slot still admits a pod. The 2-VM cap is not raised. |
| Shutdown during a stuck boot | `Close` returns after 30s and keeps the slot. Process exit then waits up to 5s more. If `Start` returns in that window the VM is stopped and the slot is released once. If it does not, the pod UID or warm slot id is logged and written to `cache/abandoned-boots.json` (mode 0600) by writing a sibling `.tmp` and renaming it. The next start deletes that bundle when the slot is not held, and does not pin a slot for it. A truncated record, or a leftover `.tmp`, is removed and does not keep the bundle. |
| Crash before the next start | A killed process leaves pod bundles, warm leftovers, and cache-store `.old`/`.tmp` files. The next start deletes unheld bundles, keeps a bundle whose slot is held, and republishes a committed cache store. An image left only under `cache/image-replacing/<key>` is published when `images/<key>` is missing and the tree has provenance; `image-partial` is deleted and never published. A symlink inside those directories, or one standing in for `pods`, `cache-store`, `image-partial`, or `image-replacing`, is removed as a symlink and is not followed. Break-glass sockets named `darwin-console-<16 hex>.sock` in the temp directory are removed at process start, before any pod listens. What happens to the pods is the process-restart row. |
| Process restart | A restart, crash, or host reboot stops the VMs. Leftover pod directories are deleted and are not booted as live machines. `restartPolicy: Never` becomes `Failed` / `NodeRestarted` and is not started again; its restart count stays as it was. `Always`, `OnFailure`, and an empty policy start again and the restart count increases by one. A pod that was already `Succeeded` or `Failed` keeps that phase and exit code. Drain the node before each upgrade so this path is not how a rollout stops work. |
| Start retry | Image pull, VM boot, and the guest-agent dial are retried until they succeed, the error is permanent, or the pod is deleted. The wait starts at 1s, doubles, and is capped at 30s, with jitter. The VM slot stays held and the pod stays `Pending` with reason `BackOff`, so a ReplicaSet does not replace it and a second VM is not admitted into that slot. Auth denied, an invalid image, a size or cycle limit, and a delta whose base is itself a delta are not retried: the pod fails and the slot is released. A pull deadline and a registry read stall are retried. The dial budget on each attempt is `AgentReadyTimeout` (default 2m, `--agent-ready-timeout`), which covers a boot of about 48s. |
| Host health probe | A failed host probe (disk, CPU, or memory), an unavailable VM runtime, or a cache directory that cannot be written sets `Ready=False`. Memory and disk pressure become `Unknown` only when the host probe itself failed; a runtime or cache failure keeps the last real pressure bits. `Ping` still returns nil so the node status patch and the lease continue. New pods are rejected until the next successful probe. Pods already running are left in place. |
| Workload exit phase | A guest `Exit` of 0 with `RestartPolicy` `Never` or `OnFailure` sets phase `Succeeded`, `terminated.exitCode` 0, and reason `Completed` (or the guest reason). `Always`, and an empty policy, restarts the VM and the pod stays `Running`; the container `restartCount` increments. A non-zero code under `Always` or `OnFailure` restarts the same way. `Never` with a non-zero code stays `Failed` and publishes that code. Codes below 0 are stored as 0 and codes above 255 as 255; a guest can still report 0. A stop with no guest code stays `Failed`: `VMStatus.ExitCode` when the runtime set one, otherwise 1, reason `VMStopped` or `VMFailed`. A guest reason of 1–128 characters, starting with a letter and continuing with letters or digits (`OOMKilled`), becomes `terminated.reason`; anything else leaves the host reason. Guest text written to PodStatus or an event is truncated to 1024 printable UTF-8 characters. Delete, drain, and eviction of a pod whose workload has not exited set `Failed` with exit 137 when the grace period is 0 (SIGKILL) and 143 otherwise (SIGTERM), reason `Error`. A pod that is already `Succeeded` or `Failed` keeps that phase and code. The Virtualization.framework runtime still does not set `ExitCode`. `darwin-guest-agent run -- <command>` sends the workload's code (`Completed` for 0, `Error` otherwise, `128+N` for a signal) and then halts. The send gives up after 2s. An agent with no `run` command still does not invent a code. A liveness restart drops the previous code. The VM liveness probe still fails the pod after more than 5 restarts. |
| Pod label and annotation updates | Applied to the running pod. Virtual-kubelet rebuilds container env from a map, so a reordered env slice is the same spec. Any other spec change is rejected and the VM keeps its slot. |
| Hybrid sidecar startup probe | Past the failure threshold the container is killed and the pod restart policy applies. `Always` and `OnFailure` start it again and the pod stays up, holding its VM slot. `Never` fails the pod with the runtime exit code (137 for the kill). A runtime that cannot stop the container still fails the pod and releases the slot. Liveness and readiness do not run until this probe has passed. |
| Hybrid sidecar liveness and readiness | Liveness past the failure threshold kills the container and uses the same restart policy and crash backoff as an exit. The VM is not restarted. Readiness does not kill the container: the container and the pod stay unready until `successThreshold` successes, and a later `failureThreshold` of failures clears Ready with reason `ReadinessProbe`. The slot stays held. HTTP and TCP probes dial the sidecar's own address from Docker inspect. An empty host, `localhost`, or a loopback address means that address. Any other host is rejected and is not dialed. The message on the pod and on the probe event is `HTTP <code>`, `probe dial failed`, `probe timed out`, or `probe canceled`. The response body is not included. A named port is resolved from that container's ports and dialed on the container address. An unknown name stays port 0 and the probe fails; it is not dialed. If the Mac cannot route to the Docker bridge, the probe fails with `probe dial failed`. |
| Probe period | Each startup, liveness, and readiness probe, on the VM and on a sidecar, waits its own `periodSeconds` (default 10s) after the previous sample. The first sample after the container starts, and the first after a restart, is not delayed by that period. `initialDelaySeconds` still applies. Sidecar probe I/O does not run on the watch, so a slow sidecar sample does not hold the next VM sample. The watch applies the result and joins those goroutines before it returns. The watch still wakes at least every `ProbeInterval` for exits, volumes, and backoff. A finished sidecar probe wakes it sooner. |
| VM probe thresholds | VM startup and readiness use the same consecutive-sample streak as a sidecar. Readiness starts false and becomes Ready after `successThreshold` successes (default 1), then stays Ready until `failureThreshold` failures (default 3). Startup stays not-started until `successThreshold` successes; `failureThreshold` failures fail the pod. Liveness restarts the VM after `failureThreshold` failures, and one success clears that streak (`successThreshold` is 1). `initialDelaySeconds`, `periodSeconds`, and `timeoutSeconds` apply to all three. A liveness restart clears the three streaks. The pod still fails after more than 5 liveness restarts. An `httpGet` or `tcpSocket` port that is a name is resolved from that container's `ports`. An unknown name stays port 0 and the probe fails; it is not treated as no probe. The same resolution applies to sidecar probes. |
| `kubectl logs` of the VM | The agent ring holds the workload's stdout and stderr (8 MiB, lines capped). `kubectl logs --timestamps` prefixes each line with the UTC time it was written. Without the flag the line is raw. A follow that falls behind is still dropped. Output from a process the agent did not start is not captured. |
| VM `command`, `args`, `env` | `command` replaces the image entrypoint and is the guest workload. `args` are appended. `env` values are the process environment, including a `valueFrom` virtual-kubelet already resolved into `value`. `workingDir` is the process directory. `args`, `env`, or `workingDir` without `command` is rejected, because the host cannot see the image entrypoint. `envFrom` is rejected. A `valueFrom` whose `value` is still empty is rejected. A pod that sets none of these does not call the guest, so an older agent keeps the image entrypoint. An older agent that is sent a command returns `unknown_method` and the pod fails with `command was not applied`. `darwin-guest-agent run` and a pod `command` together fail with `workload already started`. |
| Guest agent session | The agent is reached only over vsock. There is no TCP fallback. The agent closes a session after 30s with no frames when no interactive exec is open. The host sends `Health` every 10s, one third of the idle time the guest advertises (`idleMs` on handshake; an older guest that omits it is treated as 30s). A dropped session is dialed again, backoff 1s doubling to 5s, for as long as the pod is running. The VM is not restarted for a connection drop. After 30s of consecutive failure the pod stays `Running` and is not Ready, reason `GuestAgentDisconnected`. `Started` stays true. A later dial clears that reason. No process flag. Handshake sends a protocol range and a capability list; the session keeps the intersection. An older agent that omits the list still connects, with an empty set. Control frames are capped at 64 KiB. Stream and materialize frames may be 16 MiB. A larger frame, or JSON nested deeper than 32, closes the session. |
| Exec stdin | A guest that advertises `stdinWindow` (1 MiB) grants those bytes back as the process reads them. The host does not drop frames, and EOF is a frame that waits for credit. A non-TTY exec frees its slot when the process exits, including when the client has not sent EOF. An older guest advertises no window. The host then sends without waiting, and that guest can still drop a full queue. A new guest talking to an older host does not drop stdin; the older host ignores the credit frames. `kubectl exec` returns the command's exit code. A non-zero status is that code, not a transport error. A transport failure is still a plain error and does not invent a code. |
| GPU scheduling | `darwin.node/metal` is a token, not isolation. See [gpu.md](gpu.md). |
| hostPath | Shared into the guest via virtio-fs. Semantics ≠ Linux bind-mount. A sidecar bind resolves symlinks and checks the allowlist again; Docker receives the resolved path. A target outside the allowlist is rejected. |
| Sidecar isolation | Each pod's sidecars share one bridge network, removed with the pod. `runAsUser`, `runAsGroup`, `readOnlyRootFilesystem`, and dropped capabilities are applied, and `no-new-privileges` is set. `privileged`, `allowPrivilegeEscalation: true`, added capabilities, `hostNetwork`, `hostPID`, `hostIPC`, and `docker.sock` are rejected before a VM slot is taken. `runAsNonRoot` needs an explicit non-zero `runAsUser`; the image `USER` is not inspected. `supplementalGroups`, `fsGroup`, seccomp, and AppArmor are not applied. The bridge is not internal, so the daemon gateway can still reach the host network. Sidecars in the same pod can reach each other. |
| Sidecar env, pulls, limits, logs | `valueFrom` for a config map, secret, field, or resource is resolved. `envFrom` and `subPathExpr` are rejected. `subPath` must stay inside the volume after symlink resolution; missing directories are not created. CPU and memory limits are Docker's hard cap. Requests set shares and memory reservation, and they are the cap when no limit is set. Image pulls use the pod's `imagePullSecrets` matched to that image's registry. `kubectl logs` with no tail returns the whole log. `kubectl exec` copies stdin. An exec probe's stream closes when its context ends. |
| DaemonSets | Must not request a VM slot. This node does not run node-exporter as a VM. Scrape darwin-node `/metrics` on `--metrics-address` (default `127.0.0.1:9102`). |
| `kubectl top` / `/metrics/resource` | metrics-server reads `container_cpu_usage_seconds_total` and `container_memory_working_set_bytes`. When the guest advertises the `metrics` capability and the call succeeds, those values are the guest's own samples (the CPU counter is the integral of an instantaneous nano-core rate; the first sample is 0). They are untrusted telemetry from a root guest, not an input to scheduling. Scheduling uses the host probe and the pod's requests. An older agent, or a failed sample, does not publish zeros: the series are the configured VM allocation (requests, or the 2 CPU / 4Gi default) and carry `source=allocation`. That is the VM size, not measured use. Sidecar CPU is not included. Node series come from the host probe. |

| `VirtualMachine` / `VirtualMachineTemplate` CRDs | Phase 6+ |

## What *does* work (Phase 1-5 contract)

- Node registration, leases, taints, honest capacity.
- Create/delete pods, status, conditions, events.
- Hybrid pods (VM + host sidecars).
- Guest Agent exec, logs, probes (exec/httpGet/tcpSocket).
- emptyDir, hostPath, ConfigMap, Secret, projected, downwardAPI.
- Image pull with dockerconfigjson, digest verify, clonefile CoW.
- NAT + bridged, hostPort, agent-reported PodIP.
- Graceful stop via agent `Shutdown` (`sync`, then `shutdown -h now` on macOS), then VZ stop. Sync failure still halts. Off macOS both steps are no-ops so tests do not power off the machine.
- Metrics (Prometheus + kubelet stats summary) and OTLP traces.
- launchd install for the host agent and the guest agent.
