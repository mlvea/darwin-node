Kubernetes assumes capacity is fungible. On an Apple Silicon Mac, the hypervisor disagrees — twice, exactly, by law. This is the architecture tour of darwin-node: a node that runs native macOS virtual machines as pods, and treats that constraint as the design's center of gravity.

01 · The constraint

A computer is not a container

Kubernetes has a foundational assumption so deep nobody states it anymore: capacity is fungible. A node advertises pods: 110, and the scheduler spends that budget one pod at a time, trusting that pod 111 will fit tomorrow once today's workloads die. Every bin-packing heuristic, every autoscaler, every overcommit ratio rests on the idea that the number in status.capacity is a soft economic fact.

On an Apple Silicon Mac running macOS workloads, it is physics. XNU's hypervisor enforces a quota of two concurrent Virtualization.framework VMs per host, and Apple's macOS license agrees with the kernel. Not “two is recommended.” Two, or the third VM_START fails.

So the unit of scheduling here is not a container. It is a computer: a full Darwin kernel, its own network stack, a Metal device, tens of gigabytes of RAM. That reframes nearly every subsystem Kubernetes takes for granted:

Normal kubelet nodedarwin-node
Pod isolationnamespaces + cgroupshardware virtualization
Marginal pod costMBs, millisecondsGBs of RAM, ~30–60 s of boot
Capacity ceilingsoft, tunablehard, enforced in-kernel
Imagetar layers over a shared kernelan entire bootable disk, own kernel
exec / logs / probesnsenter, cgroup fdsa wire protocol to a daemon in the guest
Fig. 01 The unit of scheduling changed; the API did not.

That last row is the sneaky one. On a normal node, kubectl exec is the kubelet reaching into its own kernel. Here, the kubelet must talk to another operating system over a device bus — and whatever speaks on the far end becomes part of the product. We'll get there.

First, the discipline question: how do you let a scheduler — which exists to overcommit — loose on a machine where the third VM is illegal?

02 · Admission

Capacity you cannot negotiate with

The naive approach advertises a generous capacity and rejects overflow at bind time. That produces the worst kind of failure: the scheduler believes a lie, ships workloads to a node that cannot run them, and the error surfaces minutes later as flapping events — on fire, in production.

A lie must be impossible to tell. Admission happens before any expensive work, release is idempotent, and identity is the pod's UID — because Kubernetes guarantees a recreated pod gets a new one even when it reuses a name.

The slot table is the only component allowed to decide whether a VM may exist. It is small enough to hold in your head:

// TryAcquire takes a slot for uid. Never blocks.
// A third distinct uid fails with ErrVMCapacityExhausted.
func (s *Slots) TryAcquire(uid string) error {
    if uid == "" {
        return fmt.Errorf("empty pod uid")  // anonymous capacity does not exist
    }
    s.mu.Lock()
    defer s.mu.Unlock()
    if _, ok := s.held[uid]; ok {
        return nil                          // idempotent re-admission
    }
    if len(s.held) >= s.max {
        return ErrVMCapacityExhausted       // the law, stated plainly
    }
    s.held[uid] = struct{}{}
    return nil
}

Refusing pods is only half of honesty. The other half is telling the scheduler to stop asking. When both slots fill, the node gains a NoSchedule taint and a VMCapacity condition, pushed to the API server on a 15-second heartbeat. Try it:

VMCapacity=False

slot 2 — free—

$ watching darwin-node events…
Fig. 02 Fail-closed admission, live. Fill both slots, then ask for a third.

Allocatable follows the same rule: host CPU/memory minus explicit reservations (defaults: 2 cores, 4 GiB, 20 GiB), and pods: 2 — equal to the VM count, because that is the truth, even though it makes this the smallest-capacity node in any cluster it joins. With two slots the mechanism looks like overkill; you could almost count on your fingers. But the same heartbeat carries memory pressure, disk pressure, and Metal availability. A node whose status is recomputed from reality on a timer is a node you can reason about at 3am. One whose status was computed at boot is a museum exhibit.

03 · Images

Shipping operating systems as OCI artifacts

A macOS VM image is not an app. It is a bootable disk — tens of gigabytes containing a kernel, frameworks, and whatever toolchains the tenant needs — plus an auxiliary storage file holding the machine's identity, plus a hardware-model blob describing which Mac the disk believes it lives in.

We ship these as OCI artifacts anyway. Not Docker images — plain OCI, pulled with ordinary registries via ORAS. That buys the boring superpowers for free: auth, proxies, mirrors, air-gapped bundling, retention policies, and a world of registry operators who already know how to store these blobs. The price is that registries speak manifest-and-tarball, not hypervisor-ready-disk, so the puller rebuilds a bootable artifact from parts. Three problems fall out of that:

Which blob is which?

A registry will happily serve five layers with unhelpful names. Layers are identified by media type first and exact title second — never substring heuristics. If nothing identifies a disk, an aux, and a config, the pull fails immediately. A partial image is worse than no image: it fails forty seconds later, somewhere that looks like a bug in something else.

Decompressing tens of gigabytes shouldn't allocate tens of gigabytes

Disk images compress beautifully — most of any macOS volume is zeros — so the transform is gzip-in, sparse-file-out. The inflater streams through a writer that skips all-zero megabyte pages entirely, leaving real holes that APFS never materializes:

const sparseBlock = 1 << 20  // 1 MiB pages

for {
    n, err := io.ReadFull(r, buf)               // one reusable 1 MiB buffer
    if n > 0 {
        if !bytes.Equal(buf[:n], zeroBlock[:n]) { // all zeros?
            f.WriteAt(buf[:n], off)                // …then write nothing at all
        }
        off += int64(n)
    }
    // …
}
f.Truncate(off)   // trailing zeros become length, not data

The file's logical size matches the image bit-for-bit — the hypervisor cares — while its physical footprint lands near the compressed size. A 64 GiB image typically occupies single-digit GiB of real blocks.

How do you know the disk you booted yesterday is the disk you pulled?

Registries verify compressed-blob digests in transit; we anchor expectations harder. As each descriptor arrives, its uncompressed digest and size are recorded from OCI annotations into a provenance.json lockfile beside the materialized image. Verification on later starts is then O(1): a sidecar cache keyed by (expected digest, expected size) matches, or a full SHA-256 pass settles it. Integrity is anchored to content and expectations — never mtimes. Mtimes are suggestions; digests are facts. And the whole cache directory is 0700, because a bootable OS image is not just data. It is code, waiting to be run.

04 · Copy-on-write

Cloning an operating system in microseconds

Here is where the Mac pays rent. Every pod start clones the golden image with a single clonefile(2) call — and APFS copies the inode, not the bytes. Extents are shared with the origin until one side writes, at which point just that extent breaks off:

immutable
pod A overlay
clonefile()
pod B overlay
clonefile()
clone cost ~µs ×2 syscalls new blocks A 0 · B 0
Fig. 04 Blue extents are shared with the golden image. Amber and violet are blocks a workload dirtied — the only bytes that exist twice.

Cost per pod start: two syscalls and microseconds. Cost per pod in blocks: whatever the guest actually dirties. With a two-slot host, image churn is essentially free and cold-starts are bounded by VM boot rather than by copying tens of gigabytes.

Crash semantics come free too. Golden images are opened by nobody; overlays are owned by exactly one pod UID; anything orphaned is collected by a 24-hour sweep at boot. The invariant fits in one sentence: goldens are immutable, overlays have exactly one owner, and nothing else exists.

05 · The agent

A control plane inside every VM

Once the VM boots, the host needs to reach inside it: exec, logs, probes, network info, volume placement, graceful shutdown. On a normal node that's nsenter. Here it's a wire protocol, and we had opinions about the wire. The transport hierarchy is short and strict:

preferredvsock — device-bus sockethost↔guest, point-to-point by hypervisor-assigned CID. Not routed. Not reachable from other VMs. No IP stack involved at all.

Over whichever transport flows a framed JSON protocol. One envelope, length-prefixed, with an ID that turns a single connection into a multiplexer: requests carry it, responses return it, the client demuxes into per-call channels. Probes, health checks, and exec streams share one vsock without head-of-line blocking — provided the server also refuses to run handlers serially, which it does: every post-handshake request gets its own goroutine behind an in-flight semaphore, and slow consumers get dropped with consumer_too_slow instead of stalling the reader.

06 · Boot

The boot path, timed

Pod creation is where every subsystem meets, so it deserves a timeline. Every number below is a real configuration value. Press play — the animation compresses roughly 40 seconds of wall-clock into 14:

t+0.0s
Fig. 09 From kubectl apply to Ready. Events appear exactly when the engine emits them; the 45-second dial cap and 10-second handshake deadline are load-bearing.

Two details in that waterfall carry disproportionate weight.

The MAC address lease: each pod UID gets a stable, locally administered MAC persisted across restarts — written via temp-file-rename so a crash mid-write can't corrupt it. DHCP leases stay sticky, the ARP fallback stays meaningful, and a liveness-triggered restart doesn't look like new hardware to the network.

The dial discipline: early versions tried transports sequentially — vsock accept to completion, then connect, then TCP — which let a wedged vsock consume the entire boot budget before the fallback got its turn, silently, while the user stared at Pending. Today the dial is capped at 45 seconds regardless of caller context; progress is narrated as events (Created → Starting → VMDialing → Started) so kubectl describe reads like a story instead of a shrug; and the host is strictly an acceptor — on timeout the listener closes and any late guest connection is refused. A control channel that connects to whoever knocks first is not a control channel.

07 · Hybrid pods

One foot in each world

The unique capability of this node is that a single pod can straddle two operating systems. Container zero is the Mac VM. Containers one through N are ordinary Linux containers on the host's Docker daemon, wired with the mounts and resource limits from their spec, sharing nothing with the guest but the pod's identity:

spec:
  containers:
  - name: builder              # ← macOS VM (containers[0])
    image: ci/sonoma-xcode16:25.1
    resources: {requests: {cpu: "6", memory: 24Gi}}
  - name: artifact-proxy       # ← Linux sidecar on the HOST
    image: nginx:alpine
    ports: [{containerPort: 8080, hostPort: 8080}]
  initContainers:
  - name: fetch-manifest       # ← host-side, sequential, must exit 0
    image: busybox

The classic CI topology this enables — a macOS build environment with a thin Linux logging or caching sidecar — used to require two nodes and a service boundary. Here it's one pod, one lifetime, one delete call. Init containers run sequentially on the host before the VM exists, with an explicit guard rejecting VM images in init position, because “init” that boots an operating system is a category error, not a slow start.

Volumes, with opinions about secrets

The host materializes everything materializable — emptyDir, allowlisted hostPath, ConfigMaps, Secrets, projected tokens — into a per-UID tree, shares those directories over virtio-fs, and the guest agent places them at the mount paths. Mode selection is a policy statement dressed as an implementation detail:

Projected service-account tokens are real ones — minted via the TokenRequest API with audience and expiry, not a static string pasted into a file. Bound-token semantics survive the trip into the guest. And deleting files underneath a still-running virtio-fs client is how you turn a clean shutdown into silent data loss, which is why the teardown order above is load-bearing.

NAT mode is perfectly good for kubectl exec, port-forwards, and CI drivers — and perfectly broken for Services, because kube-proxy on some other node cannot route to an address that only exists inside this Mac's NAT. Rather than let users discover that with a weekend of debugging, NAT-only nodes wear the taint until an explicit flag removes it.

PodIP comes from the horse's mouth — the guest agent reports its interfaces after DHCP — because the alternatives (ARP-table scraping, packet sniffing) are races wearing a trench coat. hostPort is a small userspace TCP proxy that binds on the host and splices bytes toward PodIP:containerPort, re-resolving destinations when a restarted VM changes address. UDP hostPorts fail loudly rather than silently doing nothing. Port-forward remains the one door marked “not yet”: the agent protocol could carry it trivially, the design note is written, and shipping half a feature is worse than documenting an absent one.

10 · Observability

Telling the truth to the scheduler

Virtual Kubelet's implicit contract is brutal: the provider is the source of truth for pod status. Everything downstream — the scheduler's assumptions, metrics-server, the HPA, the human running kubectl top — inherits whatever the provider asserts. Assert fiction and you haven't merely misreported; you've poisoned autoscaling signals cluster-wide.

Never report a number you didn't measure. If the guest agent doesn't answer, that pod's stats are omitted — a gap metrics-server tolerates — rather than replaced with capacity-as-usage, which it does not.

The reporting layer follows from that one negative rule. Node CPU and memory come from host measurement; pod CPU and memory come from the guest's own sampler across vsock, mirrored into per-container stats because kubectl top pods renders containers, not pods. Conditions and taints recompute from the live slot table on a heartbeat — vm-full appears when the second slot fills, not when the node rebooted. Events narrate the lifecycle in vocabulary operators already know (Pulling, Starting, VMDialing, Started, Killing, ProbeFailed) so kubectl describe pod tells the same story the engine is living.

The embarrassing part is how late this arrived: the first stats implementation reported host capacity as usage, which made every dashboard show a permanently saturated node and taught us the rule above the expensive way. Honesty requirements that seem obvious in retrospect usually have a scar under them.

11 · Postmortem

What we got wrong

An architecture post that only lists victories is a brochure. The ledger, in fairness:

The engine is fire-and-forget where it should be a reconciler. Pod state is written once during start and amended by probes; the VM's actual power state is read and then discarded in the status path. A guest that panics leaves a pod reporting Running until a probe notices — and “noticing” never escalates to the restart policy the spec asked for. Node-level conditions got their heartbeat; pod-level truth is still waiting for the same treatment. This is the largest open item.

Identity is keyed by namespace/name while capacity is keyed by UID. The delete-and-recreate race — a Deployment rolls, old and new briefly share a name — can wedge a record that silently ignores its replacement. Known fix, small, still undone.

Exec is half-streamed. stdout/stderr now flow live, but there is no stdin path and no pty, so kubectl exec -it — the first thing every human types — degrades to command-mode. The protocol reserves room for input frames; the plumbing is unfinished.

logs -f returns a snapshot, and log persistence for previous-container logs rides on the same unbuilt substrate. Designed, deferred, documented — and users still hit it weekly.

SIGINT kills every VM like a power cut. The delete path honors grace periods scrupulously; the process-exit path does not. A graceful drain between signal handler and engine is specified and pending.

None of these are mysteries. They are queued, evidenced, and tracked in the open — which is what an honest backlog looks like.

12 · Closing

The philosophy

Strip away the Mac-specific machinery and four rules remain. None of them is novel; all of them were expensive to learn.

Design around the constraint you cannot remove. The two-VM quota shaped admission, images, boot, and status. Fighting it would have produced a system that lies at every layer. Accepting it produced one that lies at none.

Make the wrong thing impossible before making the right thing easy. Fail-closed admission, deny-by-default hostPath, mandatory TLS, accept-only control channels — each removes a failure mode rather than handling it.

Never report a number you didn't measure. A virtual node's cardinal sin is feeding the scheduler plausible fiction. Gaps are recoverable; lies compound.

Boring components, sharp glue. ORAS, Virtualization.framework, APFS clonefile, virtio-fs, launchd, plain JSON frames — nothing exotic in the inventory. The system's character lives entirely in how the pieces are constrained, ordered, and told the truth about each other.

The Mac was never supposed to be a cloud. It has no namespaces, no cgroups, no container ecosystem, a licensing regime instead of a resource manager, and a hypervisor that counts to two. But it has the toolchain a large fraction of the world's mobile software depends on, and hardware that makes Linux runners look like they're wading through syrup.

Meeting Kubernetes halfway meant building the missing half honestly: a node that admits what it is — two computers, occasionally three processes — and lets the cluster trust it anyway.

That's the whole trick. The rest is plumbing,
and the plumbing is open.
